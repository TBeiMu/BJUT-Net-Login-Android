# 发布与签名

正式包名为 `io.github.tbeimu.gongxiaozhu`，调试包名带 `.debug` 后缀。正式版使用固定发布密钥，证书 SHA-256 记录在仓库根目录 `release-signing.sha256`；发布工作流会核对证书，拒绝签名不一致的 APK。

## 本地签名备份

当前开发机的密钥位于被忽略的 `local/signing/gongxiaozhu-release.p12`，口令位于 `local/signing/release-password.clixml`。口令使用 Windows DPAPI 加密，只能由原 Windows 用户环境解密。该目录的访问权限限制为当前用户和 SYSTEM。

保留并安全备份密钥及可恢复的口令。仅复制 DPAPI 文件到另一台电脑不能保证口令可解密；迁移前应在原用户环境中安全导出。不要将这些文件加入 Git、Issue 或构建产物，也不要为了构建方便重新生成密钥。

## GitHub Actions Secrets

发布工作流读取下列仓库 Secrets：

- `GXZ_SIGNING_KEYSTORE_BASE64`：PKCS12 密钥文件的 Base64 内容。
- `GXZ_SIGNING_STORE_PASSWORD`：密钥库口令。
- `GXZ_SIGNING_KEY_ALIAS`：发布密钥别名。
- `GXZ_SIGNING_KEY_PASSWORD`：密钥口令。

本地构建正式包时，通过环境变量提供 `GXZ_SIGNING_KEYSTORE_PATH`（密钥文件绝对路径）及后三项配置，再执行 `gradlew.bat :app:assembleRelease`。未配置签名时输出的是未签名 APK，不能作为可安装的正式包发布。不要把口令写入 Gradle 文件、命令行参数或 `local.properties`。

## 发布步骤

1. 修改 `app/build.gradle.kts` 的 `versionName`，并递增 `versionCode`。
2. 添加对应的中文更新说明，例如 `docs/releases/v0.1.1.md`；更新 README 的版本和验证状态。
3. 运行测试、Lint、APK 构建和相关实机验证；准确记录未验证部分。
4. 提交并推送代码，确认“安卓检查”工作流通过。
5. 创建与 `versionName` 对应的标签并推送，例如 `git tag v0.1.1` 和 `git push origin v0.1.1`。

“发布正式 APK”工作流会再次检查、构建、核对签名，并将 `gongxiaozhu.apk`、`SHA256SUMS.txt` 和 `update.json` 发布到 GitHub Releases。也可使用工作流手动入口，指定已存在的标签重试尚未成功的发布。已公开版本禁止覆盖历史 APK；修复请发布新版本。

## 应用内更新信息

`scripts/create-update-metadata.py` 使用 SDK 的 `aapt dump badging` 读取正式 APK 的真实包名、版本和最低系统版本，并计算文件大小和 SHA-256；中文说明来自当前标签的发布说明。生成过程核对标签与 APK，不手工填写摘要或猜测 versionCode。

`update.json` 的 schemaVersion 为 1，字段为 versionName、versionCode、packageName、minSdk、apkSize、apkSha256 和 releaseNotes。客户端从最新正式 Release 获取该文件，再从固定版本标签下载 APK；证书信任来自应用构建时读取的 `release-signing.sha256`，不信任服务器自行声明的新证书。

发布后核对三个附件齐全，实际 APK 的版本、证书、大小和摘要与元数据一致。v0.2.4 及以前需要手动覆盖安装 v0.3.0 后才能使用 App 内更新。使用隔离模拟器及虚构账号验证下载、系统安装确认和数据保留；测试低版本包与本地传输替换不公开发布。

正式版本回退功能时，用 `git revert` 保留源码历史，递增 `versionCode` 后发布修复版本，避免要求用户降级安装。

v0.4.4 增加启动更新提醒：等待可上网网络检查一次，手动“检查更新”也显示同一三按钮弹窗。忽略记录按 versionCode 单独保存在更新目录，取消下载不清除它；记录损坏时按未忽略处理，发布更高 versionCode 后可继续提醒。版本查询不触发 APK 下载，流量下载仍需本次授权。只有用户选择“立即更新”后才采用新版及替换旧下载文件；普通取消或忽略不丢失已有进度。
